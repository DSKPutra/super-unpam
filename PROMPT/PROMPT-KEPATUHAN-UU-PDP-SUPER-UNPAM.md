# Prompt: Super UNPAM patuh UU Pelindungan Data Pribadi (UU PDP)

Disusun 29 Okt 2026. Pelengkap enam dokumen lain di Project ini. **Bukan nasihat hukum.** Dokumen ini membantu menyiapkan rekayasa dan dokumentasi; penentuan peran hukum, dasar pemrosesan, dan teks kebijakan harus ditinjau penasihat hukum atau pihak kampus yang berwenang.

## 1. Kerangka hukum (yang saya verifikasi, dan batasnya)

**Sumber yang berhasil dibaca:** ringkasan teks UU di [pasal.id](https://pasal.id/peraturan/uu/uu-no-27-tahun-2022) (halaman terpotong di beberapa pasal), tinjauan [Library of Congress](https://loc.gov/item/global-legal-monitor/2022-12-18/indonesia-personal-data-protection-act-enters-into-force), serta dua ulasan sekunder tentang PP 33/2026 ([Verihubs](https://verihubs.com/blog/pp-33-tahun-2026), [cybersecurity.or.id](https://www.cybersecurity.or.id/2026/10/pelindungan-data-pribadi-berlaku-16.html)). **Teks resmi PP 33/2026 belum saya baca.** Semua nomor pasal PP di bawah berasal dari ulasan sekunder; **periksa di JDIH Sekretariat Negara sebelum dijadikan rujukan.** Kompas tidak bisa dibuka (robots).

## 2. Posisi Super UNPAM saat ini (terverifikasi dari kode)

**Yang baik:**
- Tidak ada skrip pihak ketiga, analitik, atau pelacak (pencarian `analytics|gtag|sentry` di `src` dan `public` kosong); CSP ketat (`default-src 'self'`, `connect-src 'self'`).
- Semua data masih data contoh (`src/data/demo.ts`), jadi **saat ini belum ada pemrosesan data pribadi nyata** oleh aplikasi. Kewajiban benar-benar menggigit saat data asli tersambung.
- Kamera dan lokasi diminta lewat izin browser (`Permissions-Policy: camera=(self), geolocation=(self), microphone=()`), mikrofon dimatikan.

**Yang menjadi celah (jika dipakai dengan data asli):**

| # | Temuan | Lokasi | Pasal terkait |
|---|---|---|---|
| 1 | **Tidak ada halaman privasi, pemberitahuan, persetujuan, atau kanal hak subjek data** | seluruh `src` (pencarian `privasi|kebijakan` kosong) | 20-21, 5-13 |
| 2 | **Login meminta username dan sandi akun kampus di aplikasi tidak resmi** | `App.tsx`, `src/lib/auth.ts` | 35-39 (lihat F01/F02) |
| 3 | **Peran dan status masuk di localStorage; peran bisa diganti pengguna** | `App.tsx`, `Profil.tsx` | 35-39 |

## 3. Cara memakai
1. Tempel **P00** dan **U-ATURAN** (dokumen sebelumnya), lalu **PDP-ATURAN** di bawah.
2. Urutan: **D00 (manusia) → D01 → D02 → D03 → D04 → D05 → D06 → D07 → D08 → D09 → D10 → D11**. D00 dan D09 butuh keputusan manusia.
3. Setiap prompt menghasilkan **kode + dokumen + tes** yang menjaga kepatuhan tidak mundur (D01 dan D11 punya pemeriksaan otomatis).

Tenggat akses dan koreksi 3x24 jam menurut Ps. 30 dan 32 (periksa di teks resmi): fungsi murni src/lib/hak.ts menghitung tenggat dan status "terlambat", dengan tes, dan menampilkan peringatan ke pengelola.

## D05: Minimisasi, retensi, dan penghapusan

```text
Tujuan: setiap data punya masa simpan dan cara pemusnahan yang tertulis dan dijalankan.

LANGKAH:
1. Kebijakan retensi src/data/pdp/retensi.ts dan docs/pdp/RETENSI.md: per jenis data, periode simpan, dasar, metode pemusnahan, aturan prosesor (PP Ps. 75 menurut ulasan; cek teks resmi). Nilai yang belum ditetapkan manusia diberi TODO(BAAK/LEGAL); jangan mengarang angka.
2. Perbaiki temuan: (a) payload QR (KTM, ujian, presensi) memakai ID acak berumur pendek yang diselesaikan server, bukan NIM mentah (TODO BFF; saat ini ganti dengan pengenal demo acak dan label); (b) struk pengumpulan: simpan nomor struk dan hash saja, jangan nama berkas, dan beri tombol "Hapus riwayat di perangkat ini"; (c) peran dan status masuk tidak disimpan di localStorage (selaras F02); (d) titik presensi GPS: koordinat hanya dikirim ke server untuk keputusan di dalam/luar area dan tidak disimpan setelahnya kecuali hasil keputusan, atau disimpan sesuai retensi tercatat; (e) cache layanan (Service Worker) tidak menyimpan respons berisi data pribadi untuk jalur sensitif (atur strategi `NetworkOnly`/tanpa cache untuk /api/ yang sensitif, ganti aturan NetworkFirst umum di vite.config.ts bila perlu).

5. Klasifikasi data: label umum/spesifik/anak pada tiap entri RoPA mengendalikan perlakuan (mis. spesifik tidak boleh masuk log).

KRITERIA SELESAI: tes retensi lulus; tidak ada NIM mentah di payload QR; tidak ada nama berkas di struk; cache tidak menyimpan respons sensitif; "Keluar dan hapus" membersihkan semuanya.
```

## D06: Keamanan teknis dan organisasi (Ps. 35-39)

```text
Tujuan: kontrol keamanan yang bisa diuji, sesuai risiko data.

Prasyarat: keputusan F01/F02 (jalur login). Baca dulu: PERBANDINGAN-UNIVERS-DAN-PERBAIKAN-SUPER-UNPAM.md bagian F02-F03, vercel.json, src/lib/auth.ts, App.tsx, Ktm.tsx.

LANGKAH:
1. Model ancaman docs/pdp/ANCAMAN.md (STRIDE ringkas) untuk: login/sesi, QR, unggahan berkas, MailPAM/DrivePAM, peran dosen/penguji, e-voting. Daftar aset, penyerang, kontrol, dan sisa risiko.
2. Sesi: cookie HttpOnly + Secure + SameSite, token berumur pendek, rotasi, logout menghapus sesi server, perlindungan CSRF; tidak ada token di localStorage/URL. (Mengacu F02.)
3. Otorisasi server: peran dari sesi, pemeriksaan di setiap endpoint (RBAC) dengan tes yang menolak akses lintas pengguna dan lintas peran (IDOR). Hapus pemilih peran demo dari build produksi (flag build).
4. QR: token ditandatangani HMAC/JWT server berumur 30-60 detik, sekali pakai, tanpa data pribadi (selaras D05).
5. Transport dan penyimpanan: HTTPS only + HSTS (header sudah di vercel.json? periksa dan lengkapi), enkripsi saat disimpan untuk penyimpanan objek dan basis data, pengelolaan rahasia lewat variabel lingkungan/secret manager, tidak ada rahasia di repo (jalankan pemindaian rahasia dan tambahkan sebagai langkah CI yang disarankan).
6. Unggahan: pemeriksaan tipe isi di server, batas ukuran, pemindai malware bila tersedia, domain terpisah untuk konten pengguna (sandboxed origin), nama berkas diacak, tautan unduhan ditandatangani berumur pendek.
7. Header: pertahankan CSP ketat; tambah `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy`, `X-Content-Type-Options`, `Permissions-Policy` seminimal mungkin; uji dengan skrip yang membaca vercel.json.
8. Ketergantungan: audit dependensi (npm audit atau OSV) sebagai langkah CI yang disarankan, kunci versi, dan kebijakan pembaruan.
9. Pencatatan: log akses data sensitif (siapa, kapan, apa) tanpa isi data; log tidak memuat NIM mentah; retensi log tercatat (D05).
10. Organisasi: peran dan akses minimum untuk pengelola, 2FA untuk akun pengelola (GitHub, Vercel, penyimpanan), daftar orang yang punya akses produksi, dan prosedur pencabutan akses.
11. Uji: skrip memeriksa header, tes otorisasi (data dua pengguna), tes bahwa build produksi tidak memuat pemilih peran demo, dan daftar periksa uji penetrasi docs/pdp/CHECKLIST-PENTEST.md untuk dikerjakan manusia/pihak ketiga.

KRITERIA SELESAI: tes otorisasi lintas pengguna lulus; build produksi tanpa pemilih peran; QR tanpa data pribadi dan kedaluwarsa; daftar periksa pentest tersedia; tidak ada rahasia di repo.
```

## D10: Perlakuan data spesifik dan pengguna rentan

```text
Tujuan: pastikan data spesifik (keuangan pribadi, anak, biometrik, kesehatan, catatan kejahatan, genetika) mendapat perlakuan lebih ketat di kode.

Baca dulu: ropa.ts, Keuangan.tsx, DompetSertifikat.tsx, Aspirasi.tsx, Booking.tsx, rencana MailPAM/DrivePAM.

LANGKAH:
1. Klasifikasi: tipe `KategoriData` dan pembantu `perluPerlakuanKhusus(kategori)`; entri spesifik wajib punya dasar pemrosesan tertulis dan DPIA (tes D01 diperluas).
2. Data keuangan (tagihan, VA, riwayat bayar): tampilkan seperlunya, jangan di notifikasi push atau judul tab; nomor VA ditutup sebagian di layar publik/screenshot-ready; tanpa penyimpanan nomor kartu (tidak ada fitur kartu; larang di kode).
3. Notifikasi dan pratinjau: isi notifikasi tidak memuat nilai, nominal tagihan, atau status kesehatan; hanya "Ada pembaruan tagihan".
4. Layar kunci dan berbagi: tombol "Sembunyikan nilai di layar" pada Nilai, Keuangan, dan KTM; tidak ada data sensitif pada URL atau judul dokumen.
5. Biometrik: jangan ada pengenalan wajah atau sidik jari di sisi aplikasi tanpa DPIA dan keputusan manusia. Passkey (WebAuthn) tidak mengirim biometrik ke server; tulis penjelasan ini di privasi bila dipakai.
6. Aspirasi dan pelaporan: kanal anonim sungguh anonim (tanpa NIM, tanpa IP tersimpan, tanpa metadata berkas); pelapor tidak dapat ditelusuri lewat log; hapus metadata EXIF dari lampiran.
7. Pengguna rentan: formulir mudah diakses (Ps. 26), bahasa jelas, jalur bantuan manusia.
8. Tes: pembantu klasifikasi, pembersih metadata (fungsi murni bila memungkinkan), dan pemeriksa isi notifikasi yang menolak pola nominal/nilai.

KRITERIA SELESAI: notifikasi tidak memuat data sensitif (tes); aspirasi tanpa identitas; opsi sembunyikan nilai berfungsi; tidak ada fitur biometrik tanpa DPIA.
```
